### ⚠ Phase 1 の予約は「予約リクエスト方式」のみ — 明文化（暴走防止）
- 顧客は希望日時・メニューを**送信できる**だけ。**予約は自動確定しない**（オーナーが見て確定/調整）。
- **対象外（NOWでは作らない）**：空き枠カレンダー / 自動確定 / リアルタイム予約 / 二重予約防止 / 枠ロック / サロン別モード切替UI。
- 予約リクエストは将来の予約システムへ発展可能な形で保存する。ただし現在は**受付が目的**で、**予約ドメイン（`reservations`）のテーブル構成は確定しない**。受付専用テーブル（例：`reservation_requests`）でよく、**Goの予約ドメインはこの段階で作らない**。後で Reservation ドメインへ移行する。移行方法・データ構造は Phase 2 で確定する。

**NOW の完成定義：** enu のHPが公開され、HPの予約リクエスト/問い合わせフォームから送信内容がDBに保存され通知が届く状態。

## 判断軸（迷ったら）

- **何を作るか（順序）= 顧客価値。** → 今は HP（実ユーザーの要望）。
- **どう作るか（実装品質）= ポートフォリオ価値。** → マルチテナント・認可・監査・テスト・ADR。
- **最大リスクは設計ミスではなく「設計のし過ぎで実装が止まること」である。** ただし、品質・セキュリティ・マルチテナント境界・データ整合性に関わる事項は妥協しない。80〜90点で固定する対象は「将来のための仮説設計」「早すぎる抽象化」「未発生の要件への備え」であり、品質要件ではない。品質を満たした時点で実装へ進み、残り10〜20%の将来最適化は必要になった時に行う。
