# ADR-004: HPB連携戦略

## ステータス
採用済み（v1：ポーリング方式）・計画済み（v1.5：Pub/Sub方式）

## コンテキスト
HPBからの予約通知をシステムに自動反映する必要がある。
以下の理由から公式API・スクレイピングは採用しない。

- HPBの公式APIは個人サービスには開放されていない
- スクレイピングはHPB側のUI変更で即座に壊れるリスクがある

Gmail APIを使いHPBの予約通知メールを取得する方式を採用する。

## 決定事項
v1ではGmail APIポーリング方式を採用する。
v1.5でGmail API Push + Google Cloud Pub/Sub方式に移行する。

## v1：ポーリング方式のワークフロー
HPB通知メール → Gmailに届く
↓
GoのAPIがGmail APIでポーリング（定期取得）
↓
メール本文を解析
↓
Reservationsテーブルに書き込み（UPSERT）

## v1.5：Pub/Sub方式のワークフロー
HPB通知メール → Gmailに届く
↓
Gmail API Push → Google Cloud Pub/Sub
↓
Go API（/api/v1/webhooks/gmail）
↓
メール本文を解析 → Reservationsテーブルに書き込み

## v1でポーリング方式を選んだ理由
- 初期フェーズのトラフィックはポーリングで十分に対応できる
- Pub/Subはローカル開発環境のテストが複雑で開発速度が落ちる
- シンプルな実装で早期にサービスを提供することを優先する

## 移行トリガー条件
以下のいずれかを満たした時点でPub/Sub方式に移行する。
- テナント数が10店舗を超えた時
- SentryでAPIレート制限（429エラー）の兆候を検知した時

## 冪等性設計
- HPBの予約番号をIdempotency Keyとして使用する
- UPSERTで重複登録を防止する
- 同じ予約通知が複数回到達しても安全に処理できる設計にする

## エラー設計
- メール本文のパースエラー発生時はSentryに自動送信する
- Slackに即座に通知し手動対応フローに移行する
- HPBのメール形式変更を素早く検知できる体制を維持する

## テナントオンボーディング
WorkOSログインとは別に、Googleアカウント連携を独立したステップとして実装する。
OAuthスコープは最小権限の原則に従い、メール読み取りのみ可能な
`gmail.readonly`スコープのみを要求する。
メール送信・削除・変更の権限は一切要求しない。

## トレードオフ
- ポーリングはPub/Subと比較してリアルタイム性が若干劣る
- HPBのメール形式が変更された場合はパーサーの修正が必要になる
