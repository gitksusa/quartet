## このドキュメントの目的

Quartet の HP 作成システムにおける、テンプレートパターンの設計を定義する。Phase 0b（Lite CMS・テナント管理画面）の最初の設計成果物であり、後続の DBスキーマ設計・管理画面UI設計・公開HP表示設計すべての土台となる。

このドキュメントは営業資料の原型も兼ねる（「御社のサロンならこの型が合います」という提案の根拠）。

---

## 最重要の設計原則

### 原則1: テンプレートは「保存項目」を変えるものではない

テンプレートは、共通セクション群の **並び順・強調度・見せ方** を変えるものとする。テンプレートごとに保存する項目（DBのカラム）を変えてはならない。

**禁止例（このようなDBにしない）:**
```
template_1_hero_title
template_2_gallery_image_1
template_3_staff_message
```

これをやると、テンプレートを追加するたびにDBスキーマが壊れ、管理画面もテンプレートごとに作り直しになる。

**正しい考え方:**
共通セクション（hero, concept, gallery 等）を先に定義し、各セクションの保存項目は全テンプレート共通にする。テンプレートの違いは「どのセクションを、どの順で、どう強調して見せるか」だけに留める。

### 原則2: 特定テナントのハードコード分岐を禁止

`slug === "enu"` のような特定テナント向けの分岐は設計ミスとして扱う。enu は最初の利用者・サンプル入力元であり、特別扱いするテナントではない。どのサロンオーナーでも、テンプレートを選び、文章・画像・セクション表示を自分で編集できる汎用システムを作る。

### 原則3: テンプレート数は6個で固定

7個以上には増やさない。柔軟性はテンプレート追加ではなく、各テンプレート内のセクションON/OFF・並び順で出す。

### 原則4: テンプレートと mood は独立 2 軸

- **テンプレ = HTML 骨格**（セクション並び・強調度・全体構造）
- **mood = デザイントークン**（CSS 変数セット：色・フォント・角丸・影・余白）

全 mood は全テンプレートで自由に組み合わせ可能とする。組み合わせの実装コストは 6×N ではなく **6+N** に抑えられる（テンプレ追加は骨格 1 パターン追加、mood 追加は Zod 許容値 + トークンセット 1 個追加のみ・migration 不要）。

DB 側の対応は `hp-db-schema.md` の 1 節参照（`tenant_site_settings` に `template_type text` と `mood text` の 2 カラムで管理）。mood の許容値は Zod で管理し、Postgres enum は使わない（原則 3 と同じく追加時 migration 回避）。

## mood パレット定義（デザイントークン）

mood は「雰囲気」を CSS 変数セット（デザイントークン）で表現する。初期セットは 3〜5 個程度で開始し、実運用で追加要望が出た段階で 1 個ずつ増やす。

### 初期セット（PR9 で確定）

| mood 識別子 | 想定される印象 |
|---|---|
| `modern` | シャープ・都会的・直線的 |
| `natural` | 柔らか・木質感・アイボリー基調 |
| `elegant` | 高級・落ち着き・深色 |

識別子は英語スネークケース。表示ラベルの日本語は `src/lib/constants/site-settings.ts` の `MOODS` 定数で持つ。

### 各 mood が持つ CSS 変数（粒度）

各 mood は以下のカテゴリで CSS 変数を持つ:

- **色**: 背景色・前景色・主張色（アクセント）・境界線色
- **フォント**: ベースフォント・見出しフォント
- **角丸**: 標準の border-radius
- **影**: box-shadow プリセット
- **余白**: 標準の gap / padding スケール

具体的な変数名・数値範囲は PR9（mood 選択実装）で確定する。原則は「テンプレの HTML 骨格を書き換えずに、CSS 変数差替えだけで見た目が変わる」こと。

### 管理方針

- **列挙値の管理はアプリ層**: `src/lib/constants/site-settings.ts` の `MOODS` 定数（TS `as const` union）を Source of Truth とする。Postgres enum は使わない（原則 3 と同じ）。Zod 化は PR11+ で検討
- **補助的な NULL / 長さ検証は DB 側にも置く**: 0007 の CHECK 制約 `tenant_site_settings_mood_length_check` により `mood` は NULL 許容、非 NULL 時は 1〜50 文字。列挙は DB 側で行わない（`docs/db/migrations/0007_add_mood_replace_read_and_add_update_rpc.sql` ヘッダ【mood の DB 側検証】参照）
- **読み取り側の正規化**: DB 側で列挙検証しないため、`getOwnerTenantSiteSettings` は `isMoodId()` 型ガードで既知値へ正規化する（未知値は null 化・UI 上「未設定」表示・STEP2 で保存すれば既知値に上書きされる）
- 追加時のフロー: (1) `MOODS` 定数に 1 値追加 → (2) CSS 変数トークンセット 1 個追加（トークン実装後）→ (3) 管理画面の mood 選択 UI に自動反映。**migration 不要**

### 独立化トリガー（将来）

mood 数が 5〜6 個を超え、各 mood のトークン仕様（変数名一覧・数値範囲・命名規約）が肥大化した時点で、この節を独立 doc `docs/design/hp-mood-tokens.md` へ切り出し、本 doc からリンクする方針とする。それまでは 1 節に収める。

## 共通セクションID 定義

全テンプレートが共有するセクションの一覧。テンプレートはこのセクション群の組み合わせ・並び順・強調度で構成される。

**重要**: `セクションID` は **安定した英語キー**である。DB に保存され、コードが参照する識別子であり、一度確定したら変更しない（変更にはマイグレーションが必要）。画面に表示する日本語ラベルは別物として扱い、このキーとは分離して管理する（表示ラベルは管理画面・公開HP側で持つ）。

| セクションID（英語キー） | 表示ラベル例（日本語） | 内容 | 主な入力項目 | 画像分類（content-image-policy） |
|-------------|------|------|-------------|-------------------------------|
| `hero` | メインビジュアル | ファーストビュー | キャッチコピー、サブコピー、背景画像 | 背景・雰囲気画像 or 実写コンテンツ |
| `concept` | コンセプト | コンセプト・サロン紹介 | 見出し、本文、画像 | 背景・雰囲気画像 or 実写コンテンツ |
| `features` | 特長・強み | サロンの強み・特長の訴求 | 見出し、各特長の項目（タイトル＋説明） | （画像任意） |
| `gallery` | ギャラリー | 施術作品・デザイン一覧 | 画像複数、各キャプション | 施術結果画像 or 実写コンテンツ |
| `menu` | メニュー・料金 | メニュー・料金表 | メニュー名、価格、説明 | （画像任意） |
| `staff` | スタッフ紹介 | スタッフ・オーナー紹介 | 氏名、肩書き、メッセージ、写真 | 実写コンテンツ |
| `voice` | お客様の声 | お客様の声・口コミ | コメント、属性 | （画像任意） |
| `access` | アクセス | アクセス・店舗情報 | 住所、地図、営業時間、最寄駅 | 実写コンテンツ（外観等） |
| `reservation` | ご予約 | 予約導線 | 予約方法、外部リンク（LINE等）、電話番号 | （画像不要） |
| `campaign` | キャンペーン | 割引・キャンペーン・クーポン | 見出し、本文、期間、対象 | 背景・雰囲気画像 |
| `faq` | よくある質問 | よくある質問 | 質問、回答 | （画像不要） |
| `recruit_cta` | 採用情報 | HP内の求人導線（求人ページへの誘導） | 見出し、短い紹介文、求人ページへのリンク | 実写コンテンツ |

**`campaign` と `news`/`blog` の責務分離（重要）**: `campaign` は「割引・キャンペーン・クーポン」（期間限定の販促）に限定する。「お知らせ・ブログ・コラム」のような継続的な情報発信は責務が異なるため `campaign` に混ぜない。これらは将来の別 section_id 候補（`news` または `blog`）として扱い、**Phase 0b では実装しない**。実装する場合は本ドキュメントに section_id を追加してから行う。

**`recruit_cta` と求人ページ本体の責務分離（重要）**: `recruit_cta` は **HP内の求人導線**（「採用情報はこちら」という誘導ブロック）であり、求人ページ本体ではない。求人ページ本体は `/[slug]/recruit`（`src/app/[slug]/recruit/page.tsx`）が担い、`tenants.is_recruit_enabled` で公開制御される。`recruit_cta` はあくまでHPトップから求人ページへ誘導するCTAであり、両者を混同しない。

**注**: 画像分類は `.claude/playbooks/content-image-policy.md` の3分類（背景・雰囲気画像 / 実写コンテンツ / 施術結果画像）に従う。特に `gallery` で施術結果画像を扱う場合は優良誤認リスクが高いため、テナント実写真のみ・出典管理が必要。

**ON/OFF とは**: 各テナントは、管理画面から各セクションを表示/非表示に切り替えられる。`reservation` のような必須級セクションを除き、原則すべてON/OFF可能とする。

## テンプレート6パターン

### 識別子一覧（code / DB で使用）

| 番号 | 識別子（snake_case） | 表示名 | 主役 |
|---|---|---|---|
| 1 | `atmosphere` | Atmosphere | 空間・世界観・雰囲気 |
| 2 | `gallery` | Gallery | 施術作品・写真主体 |
| 3 | `staff` | Staff / Artist | 施術者・オーナー |
| 4 | `conversion` | Menu / Conversion | 予約導線・料金 |
| 5 | `trust` | Trust / Treatment | 実績・信頼・技術 |
| 6 | `brand` | Brand / Multi Service | 複数サービス・ブランド |

これらの識別子は `tenant_site_settings.template_type` に **text** として保存される。

### mood との扱いの非対称性

`template_type` と `mood`（原則 4）は独立 2 軸だが、**許容値の管理方式は非対称**である。

- `template_type`: **DB 側の書き込み関数内でも許容値検証**（`docs/db/migrations/0006_upsert_owner_tenant_template_type.sql` の `NOT IN ('atmosphere','gallery','staff','conversion','trust','brand') THEN RAISE EXCEPTION` により防御）。理由: template_type は公開 HP の描画分岐（HTML 骨格の選択）に直結し、不正値が本番 DB に入ると公開 HP のレンダリングが壊れる。anon EXECUTE の書き込み関数を通す以上、関数単体で防御する必要がある。したがってテンプレ追加時は **本関数の許容値更新 migration を伴う**
- `mood`: **アプリ層の Zod で許容値管理・DB 検証なし**（`hp-db-schema.md` 節 1 参照）。理由: mood は CSS 変数トークンの差替のみで公開 HP の骨格には影響せず、不正値でもフォールバックで安全に処理できる。mood 追加は Zod 列挙値 + トークンセット追加のみで **migration 不要**

この非対称性は「不正値が本番 HP のレンダリングを壊すかどうか」の影響度の差に基づく設計判断。将来 mood 側も骨格に影響する要素を持たせる方針変更があれば、DB 側検証（mood 用の書き込み RPC）を導入する。

### テンプレート1: Atmosphere（世界観型）

- **主役**: 空間・世界観・雰囲気
- **向いているサロン**: 高単価・隠れ家・コンセプト重視の個人ネイル/エステ/リラクサロン
- **向いていないサロン**: 価格訴求で数を回したいサロン、デザイン点数で勝負するサロン
- **タブ構成（PCグローバルナビ）**: Concept / Menu / Access / Reservation /（Recruit）
- **セクション順**: hero → concept → gallery（控えめ）→ menu → access → reservation
- **Heroの見せ方**: 大きな空間写真または手元の最も美しい1枚を全画面に。テキストは最小限、余白を大胆に取る
- **画像の使い方**: 背景・雰囲気画像を大きく。点数より質。1枚あたりの面積を大きく取る
- **予約導線**: 控えめだが常時追従（スマホ下部固定）
- **ON/OFF可能セクション**: gallery, voice, campaign, faq, recruit_cta
- **必要な入力項目**: hero（コピー＋背景画像）、concept（本文＋画像）、menu、access、reservation
- **共通セクションID**: hero, concept, gallery, menu, access, reservation
- **参考サイト**: la vela tokyo, OLIVE SPA, uka

### テンプレート2: Gallery（作品型）

- **主役**: 施術写真・デザイン一覧
- **向いているサロン**: デザイン力で売るネイル/アイラッシュ/美容室、SNS集客重視
- **向いていないサロン**: 作品点数が少ないサロン、技術より空間で売るサロン
- **タブ構成**: Design / Menu / Access / Reservation /（Recruit）
- **セクション順**: hero → gallery（主役・大）→ menu → concept（短め）→ access → reservation
- **Heroの見せ方**: 作品グリッドをファーストビュー近くに。Instagram的な敷き詰め
- **画像の使い方**: gallery を主役に大量配置。**施術結果画像を扱う場合は content-image-policy の高リスク分類に該当するため、テナント実写真のみ・出典管理必須**
- **予約導線**: ギャラリーを見た直後に予約できる導線
- **ON/OFF可能セクション**: concept, voice, campaign, faq, recruit_cta
- **必要な入力項目**: hero、gallery（画像複数＋キャプション）、menu、access、reservation
- **共通セクションID**: hero, gallery, menu, concept, access, reservation
- **参考サイト**: DISCO, 青山ネイル

### テンプレート3: Staff / Artist（人物型）

- **主役**: オーナー・スタッフ・技術者
- **向いているサロン**: 指名文化が強い美容室/整体、個人の人柄で選ばれるサロン
- **向いていないサロン**: スタッフを前面に出したくないサロン、1人サロンで人物訴求が不要な場合
- **タブ構成**: Staff / Style / Menu / Access / Reservation /（Recruit）
- **セクション順**: hero → staff（主役・大）→ gallery → menu → access → reservation
- **Heroの見せ方**: スタッフまたは施術スタイルを大きく。人物写真を大判で
- **画像の使い方**: staff の人物写真を大きく（実写コンテンツ）。指名予約につながる見せ方
- **予約導線**: スタッフ指名と予約を紐付けられる導線（将来のスタッフ別予約への布石）
- **ON/OFF可能セクション**: gallery, voice, campaign, faq, recruit_cta
- **必要な入力項目**: hero、staff（氏名・肩書き・メッセージ・写真）、menu、access、reservation
- **共通セクションID**: hero, staff, gallery, menu, access, reservation
- **参考サイト**: SHIMA, MINX

### テンプレート4: Menu / Conversion（予約特化型）

- **主役**: 料金・予約導線
- **向いているサロン**: 新規集客重視・回転率重視・価格の分かりやすさで選ばれるサロン
- **向いていないサロン**: 高単価でブランド世界観を重視するサロン
- **タブ構成**: Menu / Price / Access / Reservation /（Recruit）
- **セクション順**: hero → menu（主役・大）→ campaign → gallery（短め）→ access → reservation
- **Heroの見せ方**: ファーストビュー直下にすぐ料金表と予約ボタン。迷わせない
- **画像の使い方**: 控えめ。情報（価格・メニュー）の可読性を最優先
- **予約導線**: 最強。全セクションから予約に飛べる。料金表の各項目に予約ボタン
- **ON/OFF可能セクション**: gallery, concept, voice, faq, recruit_cta
- **必要な入力項目**: hero、menu（メニュー名・価格・説明）、campaign、access、reservation
- **共通セクションID**: hero, menu, campaign, gallery, access, reservation
- **参考サイト**: TRU NAIL & EYE, ALBUM

### テンプレート5: Trust / Treatment（信頼・技術型）

- **主役**: 悩み解決・技術・効果
- **向いているサロン**: エステ/リラク/ケア系ネイル（自爪育成等）、技術の信頼感で選ばれるサロン
- **向いていないサロン**: トレンド・デザイン点数で売るサロン
- **タブ構成**: Treatment / Voice / Menu / Access / Reservation /（Recruit）
- **セクション順**: hero → concept（悩み提起）→ gallery（before/after的）→ voice → menu → access → reservation
- **Heroの見せ方**: 悩み解決・効果を訴求するコピー。信頼感のある落ち着いた画像
- **画像の使い方**: 施術風景（実写コンテンツ）＋ voice。**効果を主張する before/after を扱う場合は content-image-policy の最高リスク分類。実写真・誇張禁止・出典/同意管理必須**
- **予約導線**: カウンセリング予約への導線を重視
- **ON/OFF可能セクション**: gallery, campaign, faq, recruit_cta
- **必要な入力項目**: hero、concept（悩み・効果）、voice（お客様の声）、menu、access、reservation
- **共通セクションID**: hero, concept, gallery, voice, menu, access, reservation
- **参考サイト**: Longleage, OLIVE SPA

### テンプレート6: Brand / Multi Service（ブランド・複数サービス型）

- **主役**: 複数サービス・ブランド感
- **向いているサロン**: 複数メニュー業態を持つサロン（ヘア＋ネイル＋スパ等）、トータルビューティ。将来の複数店舗展開も見据える
- **向いていないサロン**: 単一メニューの個人サロン（過剰になる）
- **タブ構成**: Concept / Menu / Access / Reservation /（Recruit）
- **セクション順**: hero → concept → menu（カテゴリ別に複数サービスを整理）→ gallery → access → reservation
- **Heroの見せ方**: ブランド世界観を表す画像。複数サービスへの導線を整理して配置
- **画像の使い方**: サービスカテゴリごとに代表画像。ブランドの統一感を重視
- **予約導線**: サービス別の予約導線（メニューが多いため整理が重要）
- **ON/OFF可能セクション**: gallery, voice, campaign, faq, recruit_cta
- **必要な入力項目**: hero、concept、menu（カテゴリ別に複数サービスを表現）、access、reservation
- **共通セクションID**: hero, concept, menu, gallery, access, reservation
- **参考サイト**: uka, GARDEN

**複数サービスの表現について（重要）**: 複数サービス業態（ヘア＋ネイル＋スパ等）の整理は、専用の `services` セクションを新設せず、まず `menu` セクションのカテゴリ分け（`menu.categories` など）で表現する。理由：現時点で services を必要とする実テナントが存在せず、テンプレート6のためだけに共通セクションを増やすのは Phase 0b として早すぎる抽象化になるため（原則１・原則３参照）。**`services` 専用セクションは、複数サービス業態の実テナントが登場し、`menu` のカテゴリ分けでは表現が不足だと判明した時点で再検討する**（その時は共通セクションID定義に追加してから使う）。

**注**: 旧称 MultiStore から Brand / Multi Service に改称。Phase 0b 初期は「複数店舗」前提にせず「複数メニューを持つサロン向け」として扱う。複数店舗対応は将来フェーズで検討（`docs/future-architecture.md` 参照）。

## おすすめ/人気ランキング（後続実装・構想）

STEP2（mood 選択）画面の傍に「このテンプレへのおすすめ mood」を表示する UI 場所を確保する。初期実装は定数のみ、集計への移行は後続 PR で行う。

### 二段階の運用

**初期段階（PR9 時点）**: 運営・AI 選定の順位を**定数**として持ち、「おすすめ」と表記する。実データがないため「人気」とは称さない（景表法・優良誤認回避）。

**移行後（後続 PR・時期未定）**: 全テナントの `template_type` × `mood` 実選択の**匿名集計**を集計専用 SECURITY DEFINER 関数（後続で新設）で取得し、一定の閾値に達したら「人気」表記へ移行する。

### 設計方針（原則のみ・具体値は実装 PR で確定）

- **匿名集計**: 個票（どのテナントが何を選んだか）を返さず、件数のみを返す。テナント数が少ないうちに件数開示すると個別特定可能性があるため、閾値以上で開示
- **専用関数**: 既存 helper と分離し、集計専用 SECURITY DEFINER 関数として設計。返却型・閾値・匿名化ロジックは実装 PR 時に確定
- **景表法配慮**: 「人気」表記は実データ集計が閾値到達後のみ。それまでは「おすすめ」で運用
- **UI 場所は先に確保**: PR9 時点でも「おすすめ」ラベル付き mood 候補が STEP2 に表示される。将来「人気」に置き換わる時にも UI は同位置

**具体設計（返却型・閾値の数値・関数のパラメータ・匿名化アルゴリズム）は実装 PR 時に確定する**。本 doc では構想の記録に留め、空中設計をしない。

## 次フェーズへの引き継ぎ（DBスキーマ設計で決めること）

このテンプレート設計を踏まえ、次の DBスキーマ設計では以下を決める:

1. テナントが選んだテンプレートをどう保持するか（`tenants.template_type` 等）
2. 各セクションの内容（テキスト・画像URL）をどうもつか（セクション共通の保存構造）
3. 各セクションのON/OFF状態・並び順をどうもつか
4. 原則1（保存項目を共通化）を、テナント増加・テンプレート追加に耐える形でどう実現するか
5. 画像URLと content-image-policy の3分類をどう紐付けるか（特に施術結果画像の出典管理）

**この設計ドキュメントはまだ Draft。DBスキーマ設計の議論で、セクション定義や項目に過不足が見つかれば、ここに戻って更新する。**
