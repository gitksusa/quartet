# Quartet 開発における学習・理解方針

## 現状と課題
私はLaravel + Reactの実務経験はあるが、Next.js/Go/Supabase等のモダンスタックやマルチテナントSaaS設計は初挑戦である。
AIを活用して設計や実装を高速に進めているが、内容の半分以上はまだ完全理解できておらず、「完成後に面接で説明できないのではないか」という不安がある。

## 開発における優先順位

本プロダクトは実際に課金していただく商用マルチテナントSaaSである。
開発における優先順位は以下の通りとする。

### 1位：品質・正確性
- データ破壊を防ぐ
- テナント漏洩を防ぐ
- 予約整合性を守る
- ファイル作成漏れ・ドキュメント更新漏れ・設計変更時のADR更新漏れを出さない
- 「動いた」で終わらせず、エッジケース・セキュリティ観点を確認する

### 2位：完成（実装を前へ進めること）
- 決定済み事項を蒸し返さない
- 空中戦（学習目的だけの設計議論）で実装を止めない
- 小さくリリースする

### 3位：理解100%
- 理解100%は求めない
- Phase完了時に振り返る
- 面接で説明できる形へ整理する

**品質を犠牲にして完成を急いではならない。** また、理解100%を目指して実装を止めてもならない。

## AIへの依頼ルール

AIは以下の順序で判断すること。

### Step 1：品質確認（次へ進む前に必ず確認）
- 対象ファイルは存在するか（存在を前提とした指示を出す前に確認する）
- 前回指示した変更は実際に保存・反映されたか
- 関連ドキュメント（architecture.md / database.md 等）の更新は必要か
- ADR更新は必要か
- テストが必要な変更か判断し、必要なら実施・提案する
- マルチテナント境界を壊していないか（他テナントのデータが見えないか）
- URL設計・認可設計を壊していないか
- 要件・ADR・設計書と実装内容が一致しているか
- コミット前に `git status` で変更ファイル一覧を確認させ、追加・修正漏れがないか点検する

### Step 2：実装を進める
品質確認後は実装を進める。
決定済み事項の再議論で実装を止めない。

### Step 3：学習
理解不足はPhase完了後の振り返りで補う。

---

以下は、ビジネスの根幹に関わるため特に慎重に検証し、誤りそうな場合は必ず指摘すること（この論点に限り議論継続可）：
* tenant_id / slug / URL設計
* マルチテナント境界（他テナント参照防止）
* RLS / 認可設計 / Soft Delete
* 二重予約防止
* 要件と実装の不整合
* ドキュメントと実装の不整合

以下は、本番稼働後の必要性に応じて段階的に投入するため、現段階での過度な深掘りは不要：
* Terraform / OpenTelemetry / Circuit Breaker / Prometheus / Grafana / 高度なGoパターン
* 学習目的のみの設計議論

## 振り返りルール（面接対策のための資産化）

ロードマップの各Phase完了時に学習メモを作成する。
リリース（git tag）時は必要に応じて追加する。

格納場所: `docs/learning/XXX_phase_name.md`

AIに振り返りドラフトを依頼する場合は以下を情報源として渡すこと：
- git log
- 対象PRのdiff
- 詰まった箇所のメモ

記載項目：
1. 何を作ったか
2. なぜその設計にしたか
3. 他の選択肢
4. なぜ却下したか
5. 学んだこと（技術的な理解・原則・パターン）
6. 詰まった点と解決方法（トラブルシューティング・エラー対応）
7. 運用知識（仕様・制約・ツールの挙動など、知識として残すもの）
8. 面接で説明するならどう話すか
9. 次回同じ機能を作るなら何を変えるか

## メタ・ストッパー
このREADME自体も「過剰整備」の対象である。運用してみて不便がなければ、項目やフォーマットをこれ以上増やさない。ただし、品質・セキュリティ・マルチテナント境界・データ整合性を守るためのルールは削減対象ではない。
